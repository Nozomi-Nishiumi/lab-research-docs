実施要領 · Claude Code / GitHub Pages

コンテストサイトをつくり、
GitHub Pages で公開する

学生向けコンテスト企画の公式 Web サイト(概要・応募要項・スケジュール・結果発表などを載せる)を開発・公開するときの実施要領です。開発作業は Claude Code に日本語で指示して進め、公開は GitHub Pages(無料の静的ホスティング)を使います。公開先はリポジトリ ccs_dx_contest(公開 URL: nozomi-nishiumi.github.io/ccs_dx_contest)。同じ要領はこの資料サイト自体の運用にも使われています。

PART 01

準備(初回のみ)

3つのツールを揃える

GitHub アカウント・git/GitHub CLI・Claude Code

  1. GitHub アカウント ── github.com/signup で作成(無料)。大学メールで登録しておくと後で GitHub Education も申請できる。
  2. git と GitHub CLI(gh) を入れる。
    ターミナル · macOS
    brew install git gh
    PowerShell · Windows
    winget install Git.Git GitHub.cli
  3. GitHub CLI にログイン(ブラウザ認証。以後 Claude Code がリポジトリ操作に使う)。
    ターミナル
    gh auth login
  4. Claude Code を入れる。
    ターミナル · macOS
    curl -fsSL https://claude.ai/install.sh | bash
    PowerShell · Windows
    irm https://claude.ai/install.ps1 | iex
  5. ターミナルで claude を実行し、案内に従って Claude アカウントでサインインする(初回のみ)。VS Code を使っている人は、拡張機能「Claude Code」を入れるとエディタ内からも使える。
料金 ── GitHub・GitHub Pages は無料。Claude Code は Claude のサブスクリプション(または API 従量課金)が必要。プランは研究室の運用に合わせること。
PART 02

開発の進め方 — Claude Code に指示する

フォルダを作って、日本語で頼む

コードは書かなくてよい。目的・構成・雰囲気を伝えるのが仕事

  1. サイト用の作業フォルダを作る(このフォルダが原本になる。クラウド同期外の場所が無難)。
  2. そのフォルダでターミナルを開き、claude を起動する。
  3. 本格的に作り始める前に、フォルダを Git 管理にするよう頼む。以後の変更がすべて履歴として記録され、「いつでも戻せる」状態で開発できる。
    PROMPT · Git 管理の開始
    このフォルダを git 管理にして(git init)。今後は、ページの追加や
修正の区切りごとに、内容が分かる日本語のコミットメッセージで
記録していって。

    Git 管理にしておく利点:①失敗しても「さっきの変更を元に戻して」で直前のコミットに戻れる ②コミット履歴が「いつ・何を・なぜ変えたか」の開発記録になる ③PART 03 の公開(push)がそのままできる。

  4. 最初の指示で、サイトの目的・想定読者・ページ構成・デザインの雰囲気をまとめて伝える。
    PROMPT · 最初の指示の例
    学生向けDXコンテストの公式サイトを作りたい。読者は応募を検討する
学生。トップ(コンテスト概要とスケジュール)、応募要項ページ、
FAQページの3枚構成から始める。静的なHTMLのみ・外部依存は
Google Fonts 程度・スマホでも読めるレイアウトで。締切などの重要な
日付が目立つデザインにして。まず index.html から作って。
  5. 生成されたページをブラウザで開いて確認する(open index.html / Windows は start index.html。Claude Code に「開いて」と頼んでもよい)。
  6. 修正も会話で頼む。どのページの・どの箇所を・どうしたいかを具体的に。
    PROMPT · 修正指示の例
    応募要項ページの「提出物」の説明が長すぎるので箇条書きに整理して。
あとトップページのスケジュール表に「結果発表」の行を追加して。
できたらコミットしておいて。
  7. 大きく作り替えるときは、直前にコミットしてから着手させる(「いまの状態を一旦コミットしてから、トップページを作り直して」)。気に入らなければ「作り直す前の状態に戻して」で復元できる。
構成の推奨 ── ページごとに独立した単一 HTML(CSS も同一ファイル内)+相対リンク、という構成にすると、ビルド工程なしで GitHub Pages にそのまま置けます。この資料サイトもその方式です。React 等のフレームワークは、必要になってからで十分。
PART 03

GitHub Pages で公開する

方法A(推奨):Claude Code に丸ごと頼む

リポジトリ作成 → push → Pages 有効化 → URL 確認までを一括で

PROMPT · 公開指示の例
このフォルダの内容を GitHub の public リポジトリ「ccs_dx_contest」
にプッシュして、GitHub Pages(main ブランチのルートから配信)で
公開して。公開URLで表示されるところまで確認して。
今回のコンテストサイトの公開先 ── リポジトリ Nozomi-Nishiumi/ccs_dx_contest は上記の要領で作成・設定済みで、https://nozomi-nishiumi.github.io/ccs_dx_contest/ で配信されています(現在は準備中ページ)。以後はこのリポジトリに push すれば公開内容が更新されます。
実行されること ── gh repo create → git push → Pages の有効化 → ビルド完了と公開 URL(https://<ユーザー名>.github.io/<リポジトリ名>/)の確認。git 操作やリポジトリ作成の前には Claude Code が確認を求めてくるので、内容を見て承認する。

方法B:手動でやる場合

仕組みを把握しておきたい人向け(やることは方法Aと同じ)

  1. リポジトリを作って push する(PART 02 で Git 管理を始めていれば git init は不要で、最後の1行だけでよい)。
    ターミナル(作業フォルダで)
    git init
git add -A
git commit -m "initial site"
gh repo create ccs_dx_contest --public --source=. --push
  2. GitHub のリポジトリページで Settings → Pages を開き、Source を「Deploy from a branch」、Branch を main / / (root) にして Save。
  3. 数十秒〜数分で https://<ユーザー名>.github.io/<リポジトリ名>/ に公開される(index.html が入口)。
公開前の注意(コンテスト運営では特に) ── public リポジトリ+Pages はページだけでなくリポジトリの中身も全世界に公開されます。API キー・パスワードはもちろん、応募者の個人情報・審査資料・発表前の受賞者情報は、ページにもリポジトリにも絶対に置かないこと。「結果発表ページを発表日まで下書きとしてリポジトリに置いておく」も NG です(push した時点で誰でも見られる)。発表日に作って push するか、手元のフォルダ外で下書きしておくこと。
PART 04

更新の運用 — 直して、反映して

日常の更新サイクル

ローカルの作業フォルダが原本。反映は Claude Code に任せる

  1. 作業フォルダで claude を起動し、修正内容と「反映して」をセットで頼む。
    PROMPT · 更新指示の例
    応募締切を10月31日に延長することになった。トップのスケジュールと
応募要項ページの締切表記をすべて更新し、トップに「締切延長の
お知らせ」を1件追加して。修正できたら GitHub Pages に反映して。
  2. Claude Code が編集 → commit → push → Pages のビルド完了まで確認して報告してくる。
  3. 公開 URL をブラウザで開いて確認する。反映が見えないときはハードリロード(⇧⌘R / Ctrl+F5)。それでも古い場合はビルド中なので1〜2分待つ。
コツ ── 「ついでにリンク切れがないか確認して」「締切の日付が全ページで一致しているか確認して」のように、反映前の検証も一緒に頼むと事故が減ります。コンテストサイトは日付・要項の食い違いが最も起きやすいので、日付を変えるときは必ず「全ページ横断で」と指示すること。大きな変更のときは「先に変更案を見せて」と段階を分けるのも有効。
PART 05

うまく頼むコツ

指示の質 = 成果物の質

この資料サイトの開発で実際に効いた頼み方

  • 目的と読者を最初に伝える ── 「応募を検討している学生向け」「審査員向けの説明ページ」等。文章のトーンと詳しさが適切になる。
  • 修正は場所を特定して ── 「応募要項ページの『提出物』の2項目め」のように指すと、意図と違う場所を触られない。
  • 日付・数値は一元管理を意識する ── 締切・発表日・賞金額などは複数ページに散りやすい。変更時は「全ページ横断で更新して、最後に食い違いがないか確認して」まで頼む。
  • 既存ページとの一貫性を求める ── 「他のページと同じスタイル・構成で」と言えば、デザインや用語が揃う。
  • おかしいと思ったら指摘する ── 日本語表現・レイアウト・構成の違和感は遠慮なく直させる。「〜はいらない」「2/3のサイズに」のような短い指摘で十分通じる。
  • 公開タイミングを設計する ── 結果発表など「その日まで見せてはいけない情報」は、push した時点で公開されると心得る。発表当日に作成→push する運用にし、それまでリポジトリに置かない。
  • 秘密情報は渡さない・載せさせない ── 応募者の個人情報・審査資料・API キーは常に対象外。頼む側が意識するのが最後の砦。
実例 ── コンテストサイトの公開先は ccs_dx_contest(公開ページ)。また、いま見ているこの資料サイト(lab-research-docs)自体も同じ要領で「ページを作って」「◯◯を修正して」「Pages に反映して」という日本語の指示だけで開発・運用されており、コミット履歴を見ると指示と変更の対応が追えます。
