実施要領 · CCS DX コンテスト

コンテストサイトを、
コラボレーターとして改修する

CCS DX コンテストの公式サイトは、すでに GitHub Pages で公開環境が動いています。この要領は、改修メンバーがリポジトリのコラボレーターとして参加し、Claude Code で内容を改修・更新していくための、この企画に特化した手順書です。ゼロからサイトを作る場合の一般的な要領は別紙を参照してください。

PART 01

前提と体制

公開環境は構築済み

作るところからではなく、「直して push すれば公開される」状態から始まる

公開 URLhttps://nozomi-nishiumi.github.io/ccs_dx_contest/
リポジトリNozomi-Nishiumi/ccs_dx_contest(public)
配信設定main ブランチのルートから配信(index.html が入口)。main に push すると1〜2分で公開に反映される
管理者リポジトリのオーナー(コラボレーター招待・公開設定を管理し、作業状況の把握に努める)
改修メンバーコラボレーターとして招待されたメンバー(基本は1名が作業)。main へ直接 push できる
使う道具 ── 開発は Claude Code に日本語で指示して進めます。お使いの Claude アカウントのプラン(Claude Team for Scientists 等)によってこの要領の手順が変わることはありません。
PART 02

コラボレーターになる

改修メンバーがやること

  1. GitHub アカウントを用意し(無料。github.com/signup)、自分の GitHub ユーザー名を管理者に伝える。
  2. 招待が届いたら承認する:GitHub からのメール、またはリポジトリページ上部の通知で Accept invitation。
  3. 承認後、リポジトリページが開けて、Settings 以外の操作(push 等)ができるようになる。

管理者がやること(参考)

  1. リポジトリの Settings → Collaborators → Add people で、メンバーの GitHub ユーザー名を入力して招待する。
  2. 権限は既定の Write(push 可)でよい。
PART 03

手元に環境を作る(初回のみ)

ツールを入れて、リポジトリを手元に持ってくる

git / GitHub CLI / Claude Code の詳しい導入は別紙の PART 01 を参照

  1. git と GitHub CLI を入れ、ログインする。
    ターミナル · macOS(Windows は winget install Git.Git GitHub.cli)
    brew install git gh
gh auth login
  2. Claude Code を入れる。
    ターミナル · macOS(Windows は irm https://claude.ai/install.ps1 | iex)
    curl -fsSL https://claude.ai/install.sh | bash
  3. claude を起動し、案内に従って自分の Claude アカウントでサインインする(初回のみ。複数アカウントを持っている場合は、Claude Code 内で /login と打てば切り替えられる)。
  4. コンテストサイトのリポジトリを clone して、そのフォルダで Claude Code を起動する。
    ターミナル
    gh repo clone Nozomi-Nishiumi/ccs_dx_contest
cd ccs_dx_contest
claude
  5. 最初に、サイトの現状を把握させる(自分の理解にもなる)。
    PROMPT · 現状把握
    このリポジトリはコンテスト公式サイト(GitHub Pagesで公開中)。
構成と各ページの内容を確認して、どのファイルが何を担当しているか
説明して。
clone の置き場所 ── clone したフォルダが自分の作業場所になります。クラウド同期(Dropbox 等)の外に置くのが無難。壊しても git の履歴からいつでも戻せるので、恐れず触ってよい。
PART 04

改修サイクル — pull → 指示 → 確認 → 反映

作業の基本の一巡

基本はコラボレーター1名が作業し、管理者は状況の把握に努める体制

  1. もし他の人がウェブサイト更新作業をしていると思われる場合には、作業を始める前に最新化する(その人の変更を取り込む)。Claude Code に「まず pull して最新にして」と頼むか、ターミナルで:
    ターミナル
    git pull
  2. 改修内容を具体的に指示する。どのページの・どの箇所を・どうしたいか。
    PROMPT · 改修指示の例
    トップページに「応募要項」セクションを追加して。募集対象・提出物・
締切(仮でいいので目立つ配置)・応募方法の4項目。他のセクションと
同じデザインルールで。まだ push はしないで。
  3. 手元のブラウザで確認する(open index.html、または「ブラウザで開いて」)。公開前に必ず自分の目で見る。
  4. 内容が整ったら公開する。push した時点で1〜2分後に公開される。
    PROMPT · 反映指示の例
    OK。リンク切れと日付の食い違いがないか確認したうえで、内容が
分かる日本語のコミットメッセージでコミットして push して。
公開URLに反映されたことも確認して。
  5. 公開 URL で最終確認。反映が見えないときはハードリロード(⇧⌘R / Ctrl+F5)、それでも古ければビルド中なので1〜2分待つ。
公開のタイミングについて ── push = 即・公開されるので、立ち上げ段階ではあまり気にすることはありませんが、今後受賞者など個人名が出る際にはご注意ください(push した時点でページもリポジトリの中身も誰でも見られる状態になります)。
push が弾かれたら ── 自分の作業中に他のメンバーが push した合図です。慌てず Claude Code に「pull して、コンフリクトがあれば解消してから push し直して」と頼めば整理してくれます。
大きな改修は分けて ── デザイン全体の変更やページ構成の組み替えは、事前に管理者へ一声かけたうえで、「先に変更案を見せて」「一旦コミットしてから着手して」と段階を分けると安全です。
